# Quickstart: Validate Dockerfile and Infrastructure Review

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Contract**: [contracts/review-api.md](./contracts/review-api.md)

This guide validates the feature end-to-end once implemented. It intentionally does not include
implementation code; see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Backend running locally per `.github/instructions/backend-instruction.md` (FastAPI app serving `/api/v1`).
- Frontend running locally per `.github/instructions/frontend-instruction.md` (React app pointed at the
  backend's base URL).
- No cloud credentials or Docker/Terraform CLI access required — the review path never executes submitted
  content (Constitution Principle II).
- Optional: a configured Google AI Studio API key to exercise the AI-assisted path. Skipping this MUST still
  produce a valid deterministic-only review (`ai_status: "not_requested"` or `"unavailable"`).

## Setup

1. Start the backend (per backend instructions), confirming `GET /api/v1/health` returns `200`.
2. Start the frontend (per frontend instructions) and open it in a browser.

## Scenario 1: Review a Dockerfile with a known issue (User Story 1)

1. In the frontend, select `Dockerfile` as the input type.
2. Paste the example Dockerfile from [contracts/review-api.md](./contracts/review-api.md) (or PRD Section 42),
   which runs as root and uses an unpinned base image.
3. Click Review.
4. **Expected outcome**:
   - A summary shows non-zero counts.
   - At least one `HIGH` or `MEDIUM` finding references running as root or the base image, matching the
     `Finding` schema in [data-model.md](./data-model.md).
   - The original Dockerfile remains visible and unchanged.
   - If a corrected version is generated, a diff is shown with an explanation of the change.

Equivalent API-level check: `POST /api/v1/review` with `{"type": "dockerfile", "content": "<example>"}` returns
`200` with `findings` containing the expected severity and `original_content` equal to the submitted content, per
the Contract Test Expectations.

## Scenario 2: Review Terraform with public exposure (User Story 2)

1. Select `Terraform` as the input type.
2. Paste the example security-group configuration from [contracts/review-api.md](./contracts/review-api.md) (or
   PRD Section 43), which allows SSH from `0.0.0.0/0`.
3. Click Review.
4. **Expected outcome**:
   - A `HIGH` (or higher) severity finding identifies the public SSH exposure.
   - If a corrected Terraform version is generated, every change in `change_summary` carries a
     `risk_classification`, and the UI states that the configuration requires human review — never that it is
     safe to apply.

Equivalent API-level check: same request shape as Scenario 1 with `"type": "terraform"`; verify the response
matches the Contract Test Expectations for public security-group exposure.

## Scenario 3: Understand findings and export a correction (User Story 3)

1. Using either review from Scenario 1 or 2, open a finding in the UI.
2. **Expected outcome**: category, severity, location (when available), impact, and recommendation are all
   visible.
3. Open the diff view and confirm each meaningful change has an explanation.
4. Use the download/copy action for the corrected version.
5. **Expected outcome**: the exported content matches the displayed corrected version, and the original source
   shown in the UI is unchanged from what was submitted.

## Scenario 4: Graceful degradation (Edge Cases, FR-016, SC-004)

1. Submit a valid Dockerfile or Terraform review with the AI provider unavailable or unconfigured.
2. **Expected outcome**: the response still has `200` status with populated `findings` and `ai_status` of
   `"unavailable"` or `"not_requested"`; the UI clearly indicates that AI explanation/remediation is
   unavailable while still showing deterministic findings.

## Scenario 5: Input validation (FR-003, Edge Cases)

1. Submit an empty review request.
   - **Expected**: `400` with `error: "INVALID_INPUT"`.
2. Submit content larger than 1 MB.
   - **Expected**: `400` with `error: "INVALID_INPUT"` referencing the size limit.
3. Submit an unsupported `type` value (if reachable through the API directly).
   - **Expected**: `400` with `error: "UNSUPPORTED_FILE_TYPE"`.

## Success Criteria Traceability

- SC-001 (fast deterministic results): Scenarios 1–2 complete well under the 2-second static-analysis target,
  independent of AI response time.
- SC-003 (severity/evidence completeness): Findings inspected in Scenario 3 include all required fields.
- SC-004 (AI-failure resilience): Verified by Scenario 4.
- SC-005 (secret redaction): Not directly observable via UI; validate via backend unit/integration tests that
  assert redacted content never reaches AI prompts or logs.
- SC-006 (Terraform human-review labeling): Verified by Scenario 2.
- SC-008 (no execution of submitted content): Verified by inspecting that no build/apply process runs during any
  scenario above.
