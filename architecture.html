Architecture note / MVP

Dockerfile & Infra Reviewer

A static, evidence-first DevSecOps review system for Dockerfiles and Terraform configuration, with optional AI assistance for explanation and remediation.

Repository root · FastAPI + React/TypeScript + deterministic rules + optional Google AI
01 / High-level design

Separate the product surface from the review engine.

The system is intentionally stateless. The browser owns the editing experience, the API owns validation and orchestration, deterministic analyzers own the baseline truth, and the AI provider may enrich a result without becoming a prerequisite for review.

Browser UIReact page, Monaco editor, upload, tabs, export
->
FastAPI APIValidation, routing, errors, health endpoint
->
ReviewServiceSelects reviewer and coordinates the pipeline
->
Rule EngineDockerfile or Terraform static findings
->
Optional AIRedacted input, explanations, correction, diff

The response always preserves original_content. If AI is unavailable, deterministic findings still return successfully.

Client

Focused review workspace

Users select a file type, edit or upload source, submit it, and inspect findings without leaving the page.

Analysis

Evidence before opinion

Rules produce normalized findings first. AI can explain or propose changes, but cannot replace the baseline analysis.

Safety

Advisory by design

The product never executes submitted infrastructure and never claims generated Terraform is safe to apply.

02 / Low-level design

Small modules, explicit contracts.

The backend separates transport models from domain abstractions. The frontend mirrors the response contract with TypeScript types, keeping the API boundary visible on both sides.

Backend modules

Request and orchestration path

  • app/main.py creates the FastAPI application.
  • app/api/routes/review.py exposes /health and /review.
  • app/schemas/review.py validates requests and serializes responses.
  • app/services/review_service.py implements ReviewService and coordinates analysis, AI, diff generation, and observability.
  • app/models/review.py defines the Reviewer protocol and AnalysisResult.
Analyzer modules

Type-specific rule composition

  • DockerfileReviewer combines security, optimization, and reliability rules.
  • TerraformReviewer combines security and quality rules.
  • Each rule returns a normalized Finding with an ID, category, severity, evidence, impact, and recommendation.
  • Terraform extraction uses lightweight brace counting, not a full HCL parser.
AI boundary

Optional augmentation

  • ReviewAssistant exits early when no API key or no findings exist.
  • Secrets are redacted before model input.
  • Returned JSON is validated for shape, risk values, and forbidden safety claims.
  • AI failure maps to ai_status: unavailable; it does not erase static findings.
Frontend modules

Presentation and interaction

  • ReviewPage owns type, content, selected finding, and result composition.
  • useReview owns idle, loading, success, and error state.
  • reviewApi.ts posts JSON and normalizes API errors.
  • ReviewResults, FindingsList, and DiffViewer render the analysis.

03 / Runtime flows

One pipeline, two supported input types.

The type changes the reviewer and rules selected, but the surrounding lifecycle remains the same.

Review request

01
Submit

The browser sends type, content, and optional filename.

02
Validate

The API rejects unsupported types, empty text, or content larger than 1 MB.

03
Analyze

The selected deterministic reviewer runs its rule modules and calculates severity counts.

04
Augment

Optional AI receives redacted content and structured findings.

05
Respond

The API returns findings, original source, optional correction, diff, and AI status.

AI degradation path

A
Not requested

No API key is configured, or the static reviewer found nothing to explain.

B
Available

Validated explanations are merged by finding ID; a changed correction produces a unified diff.

C
Unavailable

Timeouts, provider errors, malformed JSON, or unsafe claims become an unavailable status.

D
Always preserve evidence

The deterministic findings and original content remain available in every successful review.

04 / API and data

The contract is the spine.

The formal contract lives in specs/001-dockerfile-infra-review/contracts/review-api.md. These are the fields that connect the UI, service, analyzers, and optional AI response.

ObjectKey fieldsResponsibility
ReviewRequesttype, content, filename?Defines the supported input and enforces the non-empty, 1 MB-bound request.
Findingid, category, severity, title, evidence, impact, recommendationRepresents one deterministic, actionable issue. AI may add an explanation.
AnalysisResultreview type, findings, metricsDomain result produced before AI augmentation. Summary counts are derived here.
ReviewResultsummary, findings, original, corrected, diff, AI statusComplete response consumed by the frontend and export actions.
RemediationChangechange, reason, related finding, risk, trade-offsExplains each generated change. Terraform changes require a risk classification.
Important invariant: original_content is always the exact submitted source. Recommendations are separate fields and never silently overwrite user input.
05 / Operations

Simple to run, bounded by design.

For local development, Vite serves the UI and proxies API calls to Uvicorn. There is no database or queue in the MVP.

Local runtime

Backend

GET /api/v1/health
      POST /api/v1/review

      cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload

Health check: GET /api/v1/health

Local runtime

Frontend

cd frontend
npm install
npm run dev

The Vite proxy forwards /api to 127.0.0.1:8000.

Configuration

Optional AI

Set GOOGLE_API_KEY to enable AI. The model, timeout, and content limit can be configured through environment variables.

Verification

Test surfaces

Backend contract, integration, and unit tests cover rule behavior and failure modes. Frontend tests cover review experience, accessibility, Dockerfile, and Terraform flows.

06 / Boundaries and next steps

What this architecture does not pretend to be.

These constraints are part of the design, not hidden implementation details.

Static, not executable

The system never runs docker build, terraform apply, provider initialization, or arbitrary submitted commands.

Heuristic parsing

Dockerfile checks are line-oriented and Terraform extraction is lightweight. Complex syntax can produce missed findings or false positives.

MVP lifecycle

Reviews are not persisted. Authentication, history, rate limiting, cancellation, and GitHub pull requests are outside the current boundary.

External scanners

Adapters exist for scanner-shaped output, but Hadolint, Trivy, TFLint, and Checkov are not invoked by default.

AI is advisory

Without a successful AI call, findings remain useful but corrected content and diffs may be absent.

Production hardening

Before production deployment, review dependency audit results, add operational controls, and consider parser and scanner integrations.
